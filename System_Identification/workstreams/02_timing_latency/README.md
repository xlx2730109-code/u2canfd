# 02 — 测通信周期、抖动和延迟

这里集中回答“到底慢在哪里、慢多少、稳不稳定”。所有测通信延迟的脚本、原始数据、处理结果和图片都只放这里。

不能把下面这些混成一个“延迟”：

- 主程序每一圈用了多久；
- 调用驱动发送接口用了多久；
- 新反馈隔多久真正到一次；
- 当前使用的反馈已经有多旧；
- 一次请求到相应反馈的往返时间；
- 从命令变化到关节开始响应的整体延迟；
- 通过真机和仿真曲线匹配得到的综合延迟。

特别提醒：从位置曲线看见“过了约 100 ms 才动”，不能直接说 CAN 延迟就是 100 ms，里面还混有摩擦、电机闭环和检测方法。

## 2026-09-16 实测：通信延迟是怎么测的

### 测法（两步，全程不使能电机、零力矩）

1. **给每一帧盖时间戳**。驱动收到 CAN 帧会触发一个回调函数，我在回调最前面记下 `perf_counter_ns()`（电脑单调时钟，不会倒退），这样每条反馈都有"到达主机"的精确时刻。

2. **用真机同款的流量发命令**。以 1 kHz 轮流向 8 个电机发 MIT 空命令帧（kp=0、kd=0、tau_ff=0，输出力矩恒为零，不会引起任何运动），连发 3 秒。每条命令都会让电机回一帧反馈，所以反馈流和真机控制时一模一样。

### 怎么算延迟

- 把同一个电机的反馈帧按到达时间排序，算相邻两帧的间隔；
- 间隔分成两种：**批内**（<1ms，说明帧早就到了、只是被攒着）和**批间隔**（两批之间的空档 ≈ 反馈最大时龄）；
- 第一版试过"发一条刷新命令掐表等回复"（RTT），结果中位 24ms 且 38% 超时——数字被批次交付干扰，**不可靠，已废弃**，以命令流法为准。

### 结果

| 指标 | 数值 |
|---|---|
| 每关节反馈频率 | 126 Hz（1 kHz 命令 ÷ 8 关节），**无一丢失** |
| 批内帧间隔 | ~0.05 ms（帧在缓冲里早已就绪） |
| 批间隔 p50 / 最大 | **108.7 ms / 110.7 ms**（8 关节一致） |

### 结论（答辩口径）

- 电机在总线上是**即时应答**的，慢的不是电机、不是 CAN 总线；
- 是 USB-CAN 驱动（闭源 DLL）把收到的帧攒在缓冲区，攒满或超时才交给程序，周期 ~109 ms；
- 所以真机控制器实际用的反馈：**平均旧 ~55 ms、最旧 ~110 ms**；
- 这解释了旧阶跃数据里"~116 ms 才动"的现象——当时分不清是没动还是没送到，现在定位到了。
- 对策（后续）：把该延迟作为 `delay` 项写进仿真模型；或更换支持即时交付的 CAN 驱动。

### 局限

时间戳是"到达主机回调"的时刻，看不到帧在线缆上的真实时刻（需要硬件时间戳才能量出）。但"批内 0.05ms vs 批间隔 109ms"的对比足以证明帧早已到达，结论不受影响。

桔色粗线 = 电机实际走的角度。它不是"嗖"一下滑上去的，是一级一级蹦，每级正好隔 109 毫秒
